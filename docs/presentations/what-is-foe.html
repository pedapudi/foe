an introduction

what is foe?

A runtime for coding agents that run with nobody watching — where the task, the permissions, the budget, and the definition of done are all fixed before the first model call, and everything that happens is written down.

foe
the problem

Unattended runs fail differently

Interactive harnesses lean on a person: someone approves the risky command, notices the loop, retries the flaky request, and decides when the work is done.

Hand the same agent an unattended machine and every one of those judgments is unstaffed. The failures that follow are quiet ones —

  • doing more than it was asked, because nothing bounded it,
  • touching files nobody meant to expose,
  • declaring victory without evidence, and
  • leaving no record precise enough to find out which.
foe
the answer

Replace supervision with structure

foe runs one episode at a time, and an episode is a contract:

  • the task is fixed at launch,
  • the capabilities are an explicit grant list,
  • the budget is declared up front, and
  • done has a definition the runtime can check.

Everything the person would have judged live is decided before the run — and everything the run does is appended to one log.

foe
concept 1 · the record

The log is the only state

Every episode writes one append-only JSONL log. Every model request, every streamed chunk, every tool call and result, every budget event — one file, one writer.

The discipline this buys: every model request is reconstructable from the log alone. What the model saw is derived from events, not remembered by the process — so a run can be replayed, audited, forked from any prefix, and diagnosed months later.

There is no other state. No database, no cache that can disagree with the record.

foe
concept 2 · authority

Nothing is reachable unless granted

A contract declares what the episode may touch: read roots, write roots, executables, ports, child contracts. The kernel enforces the list — filesystem rules compiled per process, not conventions asked of the model.

There is no ambient authority: no environment variables read anywhere, no search of the system path, no default network. What is not granted does not exist for the run.

Grants only narrow downward: a child episode, a tool process, a spawned executable each get a subset, never more.

foe
concept 3 · endings

Every ending is typed and honest

An episode ends in exactly one of four ways:

  • completed — the declared verifier passed, or the typed return was made,
  • blocked — the run states why it cannot continue, in a closed vocabulary of codes,
  • exhausted — a named budget ran out, or
  • failed — the machinery itself broke.

Mechanical stuck detection backs this up: identical calls or identical reasoning across consecutive steps end the run as blocked, without asking the model to notice its own loop.

foe
concept 4 · completion

Done is checked, not claimed

A contract can declare done_when: a verifier the runtime runs against the candidate result, and a schema the returned value must match.

The verifier's findings go back to the model — not done, here is why — up to a declared retry bound. Only an empty finding list completes the episode.

Every authoritative verification is recorded with the digest of the exact candidate it judged, so a later reader can check what was accepted — down to the byte.

foe
concept 5 · identity

A run's behavior has a fingerprint

Everything that shapes what the model can see and do — instructions, tool specifications, grants, budgets, workflow structure, captured executable bytes, the runtime build — resolves into one document and hashes to one contract fingerprint.

Same fingerprint, same behavior envelope. The task text and machine-local paths stay out, so one contract is comparable across tasks and hosts.

That makes change measurable: evidence gathered under a fingerprint belongs to it, and improvement means a new fingerprint judged against the old.

foe
concept 6 · budgets

Budgets are floors, not dials

Model calls, tokens, wall-clock seconds, episode count, concurrency — each is a declared ceiling the runtime enforces across the whole episode tree.

The stance matters more than the mechanism: budgets are safety backstops, sized generously so quality is never traded for thrift. A provider outage, for instance, is waited out with growing delays for as long as the seconds budget funds the next attempt — the budget, not an arbitrary retry count, is the bound.

Capability grows through better contracts and workflows — never by quietly loosening the floor.

what foe is not

Deliberate non-goals

  • Not an interactive assistant. There is no chat loop, no approval prompt. A person configures a contract; the run is then the run.
  • Not an orchestrator. foe is usually invoked by a parent agent or application; the parent owns scheduling and judgment across runs. foe owns one episode done properly.
  • Not a model. Models are reached through declared transports; the runtime itself decides nothing by inference — every runtime judgment (loops, budgets, endings) is mechanical and reconstructable.

three doors in

How a run starts

  • The command line — foe "task" runs the built-in coding workflow; foe init --repository PATH writes a complete starting contract; foe plan answers "will this work?" before anything runs.
  • Embedded — the Python package builds the contract, launches the binary, and services host tools; the model is called by your transport or by foe's own.
  • Under a host — any process can drive foe over the line-oriented protocol on standard input and output.

All three doors open onto the same room: one contract, one episode, one log.
