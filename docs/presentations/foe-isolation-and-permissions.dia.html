an explainer for new users

how foe decides what a run may touch

The isolation and permissions model, from first principles: why authority is an allow list, how a list in a JSON file becomes kernel enforcement, and where the honest limits are.

foe
why · the principle

Nothing is reachable unless granted

An unattended agent holds real authority over a real machine. Most software carries ambient authority — whatever the user account can do, it can do. For an autonomous run that default is backwards: the surprising action is exactly the one nobody reviewed.

foe inverts it. A contract declares what the run may touch, and everything else does not exist for it:

  • no environment variable is read, anywhere,
  • no search of the system path — executables by absolute path,
  • no network unless a grant implies it,
  • no file outside the declared roots.
foe
how · the vocabulary

Six kinds of grant

  • read / write — filesystem roots; a directory grants its whole subtree.
  • execute — files or directories a subprocess may run.
  • spawn — which declared child contracts may start.
  • bind — TCP ports a process may listen on.
  • task_session — whether a process may outlive the episode into the surrounding task.

Declared paths resolve to canonical form — symlinks followed, duplicates collapsed — so the enforced list is a set of real places, and two spellings of one directory are one grant.

foe
how · enforcement

The list becomes kernel rules

Grants are not instructions the model is asked to respect — they compile into Landlock rules the Linux kernel applies to each process before it runs. A denied access fails in the kernel, whatever the code inside wanted.

Three declared modes:

  • required — Landlock must be available, or the run refuses to start,
  • best-effort — enforce what the kernel offers, record what it could not,
  • off — grants stay advisory; chosen when an outer boundary (a container) is the real wall.

The log records which mode held and which kernel level enforced it, so a reader knows what a run's walls actually were.

foe
how · exactness

Execute names exact files

The lazy version of execute permission grants whole system directories and hopes. foe resolves the actual closure instead:

  • each selected executable, by canonical path,
  • the interpreter its shebang line names — followed recursively if that is itself a script,
  • the dynamic loader its ELF header names,
  • shared-library directories as read-only, because a library is loaded rather than executed.

A directory in grants.execute is honored as a declared subtree grant — a usable starting breadth — but the vocabulary can say exactly one file, and the resolved report shows whichever you chose.

how · captured executables

A run executes the bytes it was promised

Naming a path is not enough: a file can be replaced after the contract resolves and before — or while — the run uses it.

So configured executables are captured at construction: the bytes are read once, their digest joins the contract fingerprint, a private read-only copy is retained, and every invocation runs that copy by file descriptor. The configured path is never reopened.

Children inherit the same sealed copies over descriptors and re-check digest and mode before accepting them. Replace, edit, or delete the source file mid-run — the run does not change.

how · process ownership

Every process a run starts is accounted for

Filesystem walls are half the story; the other half is processes. On hosts that delegate cgroup v2, each invocation owns a process subtree: every child episode, tool, and stray grandchild a command forks lives inside it.

  • when a child episode settles, its subtree is killed recursively — nothing survives by daemonizing,
  • the reap wait is bounded, and an unreapable subtree surfaces as a named error rather than a hang,
  • a process may outlive the episode only through an explicit task_session grant — and without that grant the episode holds no kernel authority over the task boundary at all.

Without delegation the log records the observational fallback — the walls you did not get are stated, never assumed.

foe
how · narrowing

Authority only shrinks as it flows down

Every boundary inside a run gets a policy derived from — and contained in — the one above it:

  • a child episode's grants must be a subset of its parent's; resolution refuses a contract that widens,
  • a tool process gets the episode policy narrowed to its own executable and declared reach — internal runtime paths drop out,
  • a session gets the same treatment for its lifetime.

The deepest process in the tree holds the smallest authority. There is no call path that regains what an ancestor gave up.

foe
how · a worked detail

Even cleanup refuses to widen

A small case that shows the discipline. The runtime keeps private working directories — the sealed executable store, the process-tree bookkeeping — beside data it does not own. Deleting a directory requires a removal right on its parent, and the parent is shared.

The easy fix is read-write on the shared parent. foe grants instead:

  • read and removal rights on the owned directory itself,
  • directory-removal alone on the shared parent — enough to delete its own empty directory, nothing more.

The residual power is removing a sibling's empty directory — which destroys no data. The report rows name exactly these narrowed rights.

foe
how · reading what you got

foe plan answers "will this work?" first

Before any run, the plan opens with one line per question an operator asks — and every warning names the configuration key to change.

The same resolution feeds the run itself: the log's episode/start records the resolved permissions from the same policy object the kernel enforces, including captured-executable rows by digest. The report cannot be wider than the enforcement, because they are one computation.

why · the honest limits

What the sandbox does not claim

  • The sandbox is a backstop rather than a container. For hostile workloads at scale, run foe inside a container or VM and set the mode accordingly; the grants then document intent while the outer boundary enforces it.
  • Same-user processes are inside the trust boundary. Landlock confines what foe starts; it does not protect one process of your account from another.
  • Budgets and sandbox are floors. They are never tuned to make a run "work harder" — capability grows through better contracts, never looser walls.

Stating the limits is part of the model: an overestimated wall fails exactly when it matters, and a measured one does not surprise.

Working with the model, day one

  • foe init --repository . writes a working contract and tells you its tradeoffs out loud — the write grant includes version-control state, execute grants start directory-broad.
  • Narrow from there: replace directory execute grants with the exact files your task needs; foe plan shows the resolved result every time.
