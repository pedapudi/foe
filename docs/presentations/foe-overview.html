the kernel

The episode loop

Request failures are typed: a provider outage is retried with growing delays for as long as the seconds budget funds the next attempt; causes repetition cannot fix keep a fixed attempt ceiling. Arrivals — parent messages, child reports, session exits — enter only at request boundaries, through a typed inbox.

foe
the record

One log, fully reconstructable

  • Append-only JSONL, format version stated on the first event; a reader that meets a version it does not speak refuses with both versions named.
  • Derived messages — what the model sees each step is folded from events, never held as separate state.
  • Obligations — calls without results, unsettled children, open sessions are tracked and closed by settlement, so a log always ends well-formed.
  • Seeding — a new episode can start from any prefix of an existing log: fork a run at a decision point, or resume one.
  • Spill — oversized values move to files beside the log and leave a locator, so the record stays complete and the requests stay bounded.
foe
tools

Three sources, one registry, typed failures

  • Built-in — read, grep, edit, bash, session, retrieve, the opt-in python composer, and the team verbs. Defined by the runtime, described from the same constants that enforce their limits.
  • Configured — any executable, by absolute path. Its bytes are captured at construction and invoked by descriptor, so replacing the file cannot change the run.
  • Host — tools the embedding application implements and services over the protocol.

Every failure carries one code from a closed vocabulary — invalid-call, capability-denied, limit-exceeded, and the rest — with the corrective action in the message. Recovery reads codes, never error prose.

foe
workflows

Graphs of episodes, bounded before they run

Workflow nodes are tools, model episodes, or nested workflows. Data flows over declared edges; every cycle carries a firing bound; edge references and total possible firings are counted and refused at construction past fixed ceilings — a graph that could run away never starts.

foe
spawning & teams

Child episodes, and six verbs over them

A contract may declare child contracts and grant spawning them. Each child is its own process, its own log, its own narrowed sandbox — with budget reserved from the parent's pool and returned on settlement. No child outlives its parent.

The team layer is six built-in tools over that machinery: spawn, wait (with typed conditions), steer, notify, send, and team. Members message each other through the lead; the roster and queue fold from the lead's log.

One writer per log holds everywhere: messages travel over the host protocol, never by writing into someone else's file.

foe
models

Providers behind one streaming interface

  • Named providers — OpenAI-style endpoints, a subscription route, and Vertex AI, each configured with explicit credential files: no environment variables, ever.
  • exec — any executable speaking the chunk protocol on its standard streams; how the examples script deterministic models.
  • host — the embedding application answers requests itself, through the Python package or the raw protocol.

Streams record as chunks in the log — text, thinking, tool-call deltas — so a replayed request shows exactly what arrived, in order, including the errors.

foe login stores a credential and a default model once; foe plan reports the resolved route before any run.

isolation, in one slide

Granted, compiled, enforced

Grants compile to kernel filesystem rules per process; execute access names exact files and their interpreters, not directories of binaries. Configured executables run captured bytes by descriptor. Each invocation owns a process subtree that is killed, bounded, and removed at settlement.

The report is honest by construction: what foe plan and the log's episode/start state is built from the same policy object the kernel enforces.

The full story — why each choice, and its limits — is its own deck: foe-isolation-and-permissions.html.

verification & evidence

From "it passed" to bytes you can check

  • Every authoritative verifier run is a recorded event carrying the digest of the exact candidate it judged.
  • A completion can be required to cite learned evidence — claims paired with log sequence numbers that must reconstruct.
  • An evidence bundle packages a candidate contract, its retained proposal logs, and the accepted verifier result — digest-checked file by file, verifiable standalone, portable to whoever decides adoption.

This closed one real loop already: from retained failure evidence, a model repaired a broken configuration, an unchanged external evaluator confirmed the fix, and the same workflow transferred to a fixture it had never seen.

foe
the whole machine

Everything reduces to the same five claims

  • the task is fixed at launch, with a declared completion,
  • nothing is reachable unless granted,
  • stuck detection is mechanical,
  • an episode ends only by budget, verifier, or typed report, and
  • the append-only log is the only state.

Every feature above is one of these claims, made concrete.
